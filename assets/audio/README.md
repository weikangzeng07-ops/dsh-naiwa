# Laugh track — provenance and sync

## Files

| File | Role |
| --- | --- |
| `laugh.mp3` | The recording supplied by the project owner (`naiwa_laugh.mpga`, 82,381 B). Kept as the source of truth; the client does **not** play it directly. |
| `laugh-synced.wav` | The track that actually plays. 14.4196 s, 48 kHz, stereo, 16-bit PCM (2,768,608 B). Sample-aligned with the 432-frame / 30 fps animation. |
| `click.wav` | Synthesized click, generated by `tools/gen-click-sound.mjs`. |

## Why the MP3 alone cannot be in sync

The laugh animation is 432 frames at 30 fps = **14.4 s**. The authored reference
track (`naiwa/media/laugh.wav`) is **14.4196 s**, i.e. the same take plus the
encoder tail. It starts with **1.577 s of silence** while the pet winds up.

The user-supplied `laugh.mp3` is **not a different take**. Resampling it to
48 kHz and cross-correlating it against the reference gives a waveform
correlation of **0.98 at a lag of exactly 75,709 samples (1.57727 s)**:

```
reference:  [ 1.577 s lead-in ][ ............ laugh ............ ][ 2.632 s tail ]
user MP3:                      [ ............ laugh ............ ]
                               ^ starts here (0.1 s of pre-roll)
                                                               ^ ends at 11.787 s
                                                                 (in the authored pause,
                                                                  0.15 s before the
                                                                  second burst)
```

So the MP3 is the same performance with the lead-in and the final 2.63 s cut
off. Starting it at animation frame 0 makes every laugh **1.58 s early**; that
was the original "音频快于动作执行" bug. Stretching the 10.21 s file to 14.4 s
(with `playbackRate ≈ 0.709`) made the two ends meet but left every internal
laugh at the wrong moment, so the desync survived.

## How `laugh-synced.wav` was built

All cuts are in the recording's own timeline, so no time-stretch or pitch shift
is involved:

```
  1.57727 s of digital silence          (restores the trimmed lead-in)
+ the user's 10.21004 s MP3, decoded     (22,050 Hz -> 48,000 Hz, stereo)
+ reference[11.78731 s : 14.41960 s]     (restores the trimmed second burst/tail)
= 14.41960 s total                      (692,141 samples @ 48 kHz)
```

The splice at 11.787 s falls in the authored pause (the reference is silent
from ~11.72 s to ~11.94 s), so the join is inaudible. The result's full-track
correlation with the reference is 0.969 at lag 0 (the small loss is MP3 coding
of the first 10.2 s).

The generated file is committed; the plugin has no build-time audio dependency.
To rebuild it after replacing the user recording, re-measure the offset (the
reference is the 14.4196 s take), splice at the silent pause, and update the
constants below plus `AUDIO_QS`/the URL version.

## Playback contract

- `playbackRate = 1.0`; `preservesPitch` is only a safety net.
- The media element is the **master clock** for the animation while it is
  audible (`Pet.elapsedSec`), so decoder/startup delay cannot make the picture
  run ahead.
- `AUDIO_LATENCY_MS = 50` (measured in the target Chromium: `baseLatency=10 ms`
  + `outputLatency=40 ms`). The original 170 ms came from pygame/SDL and made
  the picture lag by ~120 ms in the browser.
- Emitted clones seek to `AUDIO_LOOP_START = 1.7667 s` (frame 53) and restart
  there on `ended`, matching the clone animation loop.

With `?naiwa-debug=1` the console prints one line per second while laughing:

```
[dsh-naiwa] sync frame=58 elapsed=1.933 audio=1.983 rate=1 paused=false
```

`frame / 30` should trail `audio` by ~0.05 s (the output latency).
